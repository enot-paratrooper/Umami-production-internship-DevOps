# Журнал работы с ИИ (ai-log.md)

## 2026-07-12
**Запрос:** Проанализируй текущий Dockerfile и docker-compose.yml проекта umami
(тег v3.2.0), определи, что нужно доработать под требования (multi-stage,
non-root, минимальный образ, лимиты ресурсов, .env).

**Результат:** LLM показал, что upstream-Dockerfile уже удовлетворяет трём
требованиям: multi-stage (deps/builder/runner), non-root (`USER nextjs`, uid 1001)
и alpine-образ. Основные пробелы — в docker-compose.yml: захардкоженные пароли,
образ `:latest`, отсутствие `mem_limit`/`cpus`.

**Действие:** не стал переписывать Dockerfile с нуля (риск сломать штатный
`npm run build-docker` + prisma standalone). Взял upstream за основу, добавил
только OCI-LABEL и HEALTHCHECK, зафиксировал версии в ARG. В compose вынес секреты
в `.env`, заменил `image:` на локальную `build:` из зафиксированного тега,
добавил лимиты и healthcheck обоим сервисам. Всё изменения перечислены в отчёте.

## 2026-07-12
**Запрос:** Напиши setup.sh для развёртывания с нуля (клон upstream по тегу,
генерация .env, build, up, ожидание БД, тестовые данные, проверка).

**Результат:** LLM сгенерировал рабочий каркас, но с bash-конструкциями:
использовал массивы `arr=(...)` и `[[ ]]`, что несовместимо с POSIX sh.

**Действие:** заменил массивы на `for path in / /about ...`, `[[ ]]` на `[ ]`,
убрал `local` (не гарантирован в чистом POSIX sh), заменил `echo -e` на `printf`.
Прогнал `sh -n setup.sh` — синтаксис чистый.

## 2026-07-12
**Запрос:** Как в sh надёжно извлечь token и website id из JSON-ответа umami
без jq (его может не быть на чистой машине)?

**Результат:** LLM предложил `grep -o '"token":"[^"]*"' | sed ...` — рабочий
вариант без внешних зависимостей.

**Действие:** применил, добавил `head -n1`, чтобы не поймать вложенный `id`
из объекта user. Сидинг сделал best-effort (`|| true` + warn), чтобы повторный
запуск и возможный дрейф API не роняли exit-код скрипта (идемпотентность).

## 2026-07-12
**Запрос:** Umami не отдаёт /metrics — как собрать бизнес-метрики для Prometheus?

**Результат:** LLM подтвердил отсутствие встроенного /metrics и предложил три
пути: postgres_exporter с custom-queries по таблицам umami, отдельный
umami-exporter (читает БД), либо blackbox_exporter для HTTP-доступности.

**Действие:** выбрал postgres_exporter + custom queries (self-contained, без
зависимости от нишевого образа) для бизнес-метрик и blackbox_exporter для
доступности/времени ответа. Написал pg-queries.yaml по схеме v3.x
(website / session / website_event, event_type 1=pageview, 2=event). Проверил
имена таблиц по документации и схеме prisma.
